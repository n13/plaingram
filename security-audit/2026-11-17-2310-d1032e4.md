# Plaingram Security Review — Overall: LOW risk

Reviewed 2026-11-17 23:10 (UTC+8) at commit `d1032e41b94c58032364182c9bcd7731f323329b` (v0.1.3).

No critical or high-severity vulnerabilities found.

**Medium (3)**

- M-1 — `sips` HEIC conversion doesn't validate the input is a regular file (not a symlink). Low practical impact since the user picks the file.
- M-2 — `receive_loop` thread has no shutdown mechanism (resource leak on exit).
- M-3 — All `.lock().expect()` calls will cascade-crash if any thread panics while holding a lock. Consider `parking_lot::Mutex`.

**Low (6)**

- L-1: `f32` truncation in download progress for large files (cosmetic)
- L-2: `month_year` can panic on invalid date data
- L-3: `sender_name` panics if user/chat data is missing
- L-4: `save_new` filename dedup loop is unbounded
- L-5: Error messages may include filesystem paths (fine for desktop app)
- L-6: QR login link validation only checks prefix (trust boundary is appropriate)

**Key positives the reviewer called out:**

1. Safe* type system enforcing sanitization at the policy boundary
2. Image re-encoding strips all EXIF/metadata (explicitly tested)
3. Vendored `zune-jpeg` with `forbid(unsafe_code)` for untrusted JPEG decoding
4. Comprehensive Unicode attack mitigation (bidi, homoglyphs, mixed alphabets, case-mixing)
5. Keychain credential storage, API hash validated as 32 hex chars
6. Path traversal prevention with sanitized filenames and `create_new(true)`
7. Chat allowlisting gates every mutating operation
8. No direct network surface — all networking via TDLib
9. Link previews disabled on outgoing messages
10. Contact lookalike detection via skeleton matching

# Plaingram Security Review

**Date:** 2026-11-17  
**Scope:** Full codebase review of all Rust source files in `crates/tg-core` and `crates/tg-ui`  
**Reviewer:** Automated security audit

---

## Executive Summary

Plaingram is a well-architected Telegram client with a strong defensive posture. The codebase demonstrates security-conscious design through its "Safe" type system, comprehensive text sanitization, controlled image re-encoding, and explicit allowlisting of chat types. The most notable strengths are the deliberate stripping of EXIF metadata from images, the vendored JPEG decoder built without unsafe SIMD code, the keychain-based credential storage, and the thorough Unicode homoglyph/bidirectional text attack mitigation.

No critical vulnerabilities were found. The findings below are predominantly low-severity hardening opportunities and informational observations.

## Findings

### HIGH

*No high-severity findings.*

### MEDIUM

#### M-1: `sips` Command Injection via Crafted Filenames (macOS only)

**File:** `crates/tg-core/src/image.rs`, lines 76-82  
**Description:** When decoding an unsupported image format on macOS, the code invokes `/usr/bin/sips` with the user's file path passed via `.arg(file)`. While `.arg()` is not shell-interpreted (it passes the argument directly to `execv`), the `out` path is also passed and is derived from `paths::upload_path`, which uses a random hex name in the data directory. The user-controlled `file` path is passed safely via `arg()`, so there is no shell injection. However, the sips invocation does not validate that `file` actually points to an image; a symlink or specially named file could cause sips to process unexpected content.

**Impact:** Low practical impact since the user selects the file themselves (via file picker or drag-and-drop). An attacker would need the user to intentionally select a malicious file.

**Recommendation:** Validate that the file path is a regular file (not a symlink to something unexpected) before passing it to sips.

#### M-2: Unbounded `receive_loop` with No Shutdown Mechanism

**File:** `crates/tg-core/src/client.rs`, lines 464-472  
**Description:** The `receive_loop` runs `loop { ... }` with no exit condition. The thread spawned on line 117 (`thread::Builder::new().name("tdlib-updates")`) will never terminate, even when the application closes. While `td::receive(2.0)` returns `None` when there is nothing to process, the loop continues forever.

**Impact:** Resource leak on application shutdown. The thread continues to run until the process exits, which on macOS is fine for a desktop app but could cause issues if the client is ever used in a library context.

**Recommendation:** Add an `AtomicBool` shutdown flag checked each iteration, or break from the loop when a `Closed` state is handled and no restart is expected.

#### M-3: Panics on Poisoned Mutex Locks

**File:** `crates/tg-core/src/client.rs`, lines 357, 721, 728; `crates/tg-core/src/text.rs`, line 221  
**Description:** All mutex lock acquisitions use `.expect("... lock poisoned")`, which will panic if any thread panics while holding the lock. While mutex poisoning is rare in well-tested code, this means any single panic in a thread holding `uploads`, `allowed`, or `REPORTED` will cascade into panics throughout the application.

**Impact:** A single panic in an async task (e.g., from a malformed TDLib response) while holding a mutex could crash the entire application.

**Recommendation:** Consider using `parking_lot::Mutex` which does not have poison semantics, or handle the poisoned case gracefully (the data is likely still valid).

### LOW

#### L-1: `download_progress` Division Uses `as f32` Truncation

**File:** `crates/tg-core/src/policy.rs`, line 92  
**Description:** `file.local.downloaded_size as f32 / file_size(file).max(1) as f32` uses `as f32` casts on `i64` values. For files larger than 2^24 bytes (~16 MB), the `f32` representation loses precision. This is clamped to 0..1 so it cannot produce invalid values, but progress could appear to jump or stall for large files.

**Impact:** Cosmetic only; progress bar may not be perfectly smooth for files over ~16 MB.

**Recommendation:** Consider using `f64` for the intermediate calculation before converting to `f32`.

#### L-2: Potential Panic in `month_year` on Invalid TDLib Data

**File:** `crates/tg-ui/src/app.rs`, line 1900  
**Description:** `NaiveDate::from_ymd_opt(year, month, 1).expect("month is 1 to 12")` will panic if `month` is not in 1..=12. While `account_info` in policy.rs filters to this range, the function is public and could be called with unchecked data.

**Impact:** Panic on malformed data. The filtering in `policy.rs` makes this unlikely in practice.

**Recommendation:** Return a fallback string instead of panicking, since this is UI-facing.

#### L-3: `sender_name` Panic in Confirm Dialog

**File:** `crates/tg-ui/src/app.rs`, line 1461  
**Description:** `self.sender_name(sender).expect("TDLib sends a user or chat before referring to it")` panics if the `users` or `chats` HashMap does not contain the referenced sender. While TDLib is expected to send user/chat updates before messages, a race condition or dropped event could violate this assumption.

**Impact:** Application crash if a user or chat event is missed or arrives out of order.

**Recommendation:** Return a fallback "Unknown" display name instead of panicking.

#### L-4: `save_new` Infinite Loop Possibility

**File:** `crates/tg-core/src/paths.rs`, lines 65-81  
**Description:** `for copy in 0..` iterates indefinitely when looking for an unused filename. While practically unreachable (it would require billions of collisions), the unbounded range means the function never returns `Err` for a full directory.

**Impact:** Theoretical hang if the Downloads directory is pathologically full of colliding names.

**Recommendation:** Cap the counter (e.g., at 10,000) and return an error.

#### L-5: Error Messages May Leak Internal Paths

**File:** `crates/tg-core/src/client.rs`, line 687  
**Description:** `self.emit(Event::Error(sanitize(&format!("{error:#}"))))` sends errors to the UI after sanitization. While the text is sanitized for Unicode attacks, `anyhow::Error` chain formatting may include internal file paths, TDLib error codes, or system error messages.

**Impact:** Information disclosure of local filesystem paths to the user via the error banner. Since this is a local desktop app, the user already has this information, so the practical risk is negligible.

**Recommendation:** No action needed for a local desktop app. If the app ever gains remote error reporting, errors should be scrubbed.

#### L-6: QR Login Link Validation Is Minimal

**File:** `crates/tg-core/src/client.rs`, line 578  
**Description:** `ensure!(state.link.starts_with("tg://login?token="), "TDLib sent an unexpected QR code link")` validates only the prefix. The token content is not validated before being rendered as a QR code.

**Impact:** If TDLib were compromised, it could send an arbitrary link with the `tg://login?token=` prefix. However, this is a defense-in-depth check against TDLib itself, so the trust boundary is appropriately placed.

**Recommendation:** Acceptable as-is; the QR code is scanned by Telegram on another device which validates the token.

### INFORMATIONAL

#### I-1: Strong SafeText/SafeContent Type System

**Description:** The entire codebase enforces a "Safe" type barrier: all data from TDLib passes through `sanitize()` or `sanitize_name()` before reaching the UI. The `SafeText`, `SafeMessage`, `SafeContent`, `SafeUser`, `SafeChat`, and `SafeProfile` types form a comprehensive boundary. The `policy` module acts as the sole conversion layer. This is an excellent design pattern.

#### I-2: Comprehensive Unicode Attack Mitigation

**File:** `crates/tg-core/src/text.rs`  
**Description:** The text sanitizer replaces:
- Bidirectional override characters (U+202E etc.)
- Zero-width characters (U+200B etc.)
- Mixed-alphabet homoglyphs (Cyrillic "а" in Latin text)
- Control characters
- Non-breaking spaces
- Fullwidth and mathematical letter lookalikes
- Emoji that look like letters (1️⃣, 🅰️, etc.)

Additionally, `sanitize_name` enforces a single alphabet across the entire name and lowercases names that mix cases within words (catching "AIice" = "Alice" with capital I for lowercase l).

#### I-3: Image Re-encoding Strips All Metadata

**File:** `crates/tg-core/src/image.rs`  
**Description:** Both received photos (decoded then re-encoded before saving) and uploaded photos (re-encoded before sending) go through a full decode/encode cycle. This deliberately strips EXIF data including GPS coordinates, camera model, and any embedded payloads. The test `re_encoding_keeps_the_picture_and_drops_everything_else` explicitly verifies that planted data does not survive re-encoding. The comment in `Backend::save_photo` says "re-encoded so no byte from its sender reaches the disk."

#### I-4: JPEG Decoder Without Unsafe Code

**File:** `vendor/README.md`, `crates/tg-core/Cargo.toml`  
**Description:** The vendored `zune-jpeg` crate is intentionally built without its `x86` and `neon` SIMD features, which makes it `#![forbid(unsafe_code)]`. This eliminates an entire class of memory safety bugs in the JPEG decoder that processes untrusted images from strangers. Similarly, `jpeg-encoder` is built without SIMD. The decode limits (`MAX_SIDE: 4096`) prevent decompression bombs.

#### I-5: Keychain-Based Credential Storage

**File:** `crates/tg-core/src/client.rs`, lines 34-78  
**Description:** API credentials and the database encryption key are stored in the macOS Keychain via the `keyring` crate. The database key is 32 random bytes from `getrandom`. Credentials are never logged (the error handler sanitizes all error text). The API hash is validated to be exactly 32 hex characters.

#### I-6: Chat Allowlisting Prevents Unauthorized Actions

**File:** `crates/tg-core/src/client.rs`, lines 80-88, 731-738  
**Description:** An `Allowed` set gates every chat operation. Chats are only added to the allowlist when they pass through `policy::chat()`, which filters out bots, channels, and other unsupported chat types. Every mutating operation (send, delete, ban, react, etc.) calls `ensure_allowed(chat_id)` first. This prevents the UI from accidentally issuing commands against chats the policy layer has filtered out.

#### I-7: Path Traversal Protection in File Saving

**File:** `crates/tg-core/src/paths.rs`, lines 55-81  
**Description:** `save_new` replaces `/`, `\`, and `:` in filenames with `_`, strips leading dots, and falls back to "file" for empty names. The test at line 117 explicitly verifies that `../../etc/passwd` becomes `_.._etc_passwd`. Files are always saved inside `~/Downloads` with `create_new(true)` to prevent overwriting. Downloaded files are quarantined on macOS via `com.apple.quarantine`.

#### I-8: Relaxed Ordering on `AtomicI32` for TDLib Client ID

**File:** `crates/tg-core/src/client.rs`, lines 639  
**Description:** `Ordering::Relaxed` is used for the TDLib client ID and the `use_phone` flag. This is acceptable because:
- The client ID is set once per TDLib instance and read by tasks spawned after the write.
- The `use_phone` flag is a simple boolean that does not guard other data.
- TDLib's own synchronization handles the actual protocol state.

#### I-9: TDLib FFI Safety

**File:** `crates/td/src/lib.rs`  
**Description:** The `unsafe` blocks in the TDLib FFI are minimal and well-justified:
- `td_create_client_id()`: pure function returning an ID.
- `td_send()`: receives a CString whose lifetime extends beyond the call.
- `td_receive()`: returns a pointer owned by TDLib, immediately parsed.
- `parse()`: null-checks the pointer, validates UTF-8, and parses JSON.

The `to_c_string` function uses `CString::new` which checks for interior NUL bytes in the JSON.

#### I-10: No Network Code Outside TDLib

**Description:** Plaingram does not make any network connections itself. All networking is delegated to TDLib, which handles TLS, certificate validation, MTProto encryption, and Telegram's end-to-end protocol. The app does not handle raw HTTP, URLs, or certificates.

#### I-11: Race Condition Window in `is_allowed` Check

**File:** `crates/tg-core/src/client.rs`, lines 731-738  
**Description:** `is_allowed` and `ensure_allowed` take a lock, check the set, and release it before the actual TDLib call. Between the check and the TDLib call, the allowlist could theoretically change. However:
- Chats are only removed from the allowlist on `AuthorizationState::Closed` (line 594), which resets the entire client.
- The TDLib call will fail with its own error if the chat is invalid.
- This is a TOCTOU pattern, but the consequence is a benign TDLib error, not a security violation.

## Positive Security Practices

1. **Defense-in-depth type system:** The Safe* types enforce that all external data is sanitized before reaching the UI. The policy module is the single point of conversion.

2. **Image re-encoding as a security boundary:** Photos are fully decoded and re-encoded before saving or displaying, eliminating embedded payloads, tracking pixels, and metadata leaks. This is explicitly tested.

3. **JPEG decoder without unsafe code:** Vendoring zune-jpeg without SIMD eliminates memory safety risks in the most attack-exposed parser (processing images from strangers).

4. **Comprehensive Unicode attack detection:** Bidirectional overrides, homoglyphs, mixed alphabets, case-mixing impersonation, invisible characters, and letter-lookalike emoji are all caught. The lookalike detection extends to contacts (skeleton matching warns when a stranger's name resembles a contact).

5. **File download quarantine:** Saved files are marked with macOS Gatekeeper quarantine attributes, treating them as internet-downloaded content.

6. **Path traversal prevention:** Filenames are sanitized and confined to `~/Downloads`, never overwriting existing files (`create_new(true)`).

7. **Keychain credential storage:** API credentials and the database encryption key never touch the filesystem in plaintext.

8. **Chat allowlisting:** Every operation is gated by an allowlist populated only by the policy layer, preventing accidental interaction with filtered chat types.

9. **Link preview disabled:** Outgoing messages explicitly set `is_disabled: true` for link previews, preventing the app from fetching URLs in messages.

10. **Thorough test coverage for security properties:** Tests explicitly verify that re-encoding strips planted data, that path traversal is blocked, that Unicode attacks are detected, and that the QR code scans correctly.

## Overall Risk Assessment

**Risk Level: LOW**

Plaingram demonstrates a security-first architecture. The codebase shows deliberate, documented decisions about trust boundaries:
- TDLib data is untrusted and sanitized at the policy layer.
- Images from strangers are decoded with a safe (no-unsafe) decoder and re-encoded before use.
- Credentials never leave the keychain.
- File operations are confined and quarantined.

The findings are limited to defensive hardening opportunities (mutex poisoning resilience, edge-case panics on malformed data) rather than exploitable vulnerabilities. The main attack surface -- processing messages and images from untrusted senders -- is well-defended by the sanitization layer and the safe image pipeline.

The application does not expose any network surface of its own; all networking is handled by TDLib's well-tested MTProto implementation. There is no web content rendering, no JavaScript execution, and no URL handling beyond QR code display.
